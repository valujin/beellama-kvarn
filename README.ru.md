# beellama-kvarn

*[English version](README.md)*

Форк [`Anbeeld/beellama.cpp`](https://github.com/Anbeeld/beellama.cpp) (который, в свою
очередь, форк [`ggml-org/llama.cpp`](https://github.com/ggml-org/llama.cpp)) с правками
KV-кэша **KVarN**: пять исправлений корректности, семь оптимизаций ядра декодирования,
две настройки расхода видеопамяти и покрытие тестами.

База — коммит `a749684` ветки `v0.4.4` апстрима, на момент снятия помеченный тегом
`preview-v0.4.4`. Наши изменения лежат сверху отдельными коммитами, каждый
соответствует одной правке; история апстрима сохранена целиком.

Оригинальный README апстрима — [README.upstream.md](README.upstream.md).
Лицензия и список авторов не менялись: [LICENSE](LICENSE) (MIT), [AUTHORS](AUTHORS).

## Числа читать вместе с условиями

Всё измеренное ниже снято на **одной машине**: одна **RTX 3090** (sm_86, 24 ГиБ),
модель **Qwen3.8-27B `UD-Q4_K_XL`**, сервер `llama-server`. У каждой таблицы свои
контекст, глубина и число слотов — они указаны, потому что эффекты зависят от всех
трёх. Это не утверждение про другие карты, другие модели и непроверенные
конфигурации.

## Чем отличается от `Anbeeld/beellama.cpp`

### Исправлено пять дефектов

| дефект | проявление |
| --- | --- |
| `structured KV live groups alias one F16 stage slot` | падение при `--kv-unified` и больше чем одном слоте: две живые группы получали один слот F16-стейджа и затирали друг друга |
| `failed to find a memory slot` при почти пустом кэше | группа считалась занятой только по факту заполненных ячеек, поэтому одновременные запросы претендовали на одну и ту же |
| устаревший план чтения между ubatch'ами | план кэшировался на весь батч, хотя состав ячеек меняется внутри батча — молча неверный вывод, зависящий от числа слотов |
| откат черновика по оси позиций ЦЕЛИ | любой запрос с картинкой ронял сервер, если черновой кэш MTP переведён на KVarN (см. ниже) |
| чтение за границей `p_sh` в ядре декода CUDA | наблюдаемое поведение не менялось, но это настоящий выход за границу массива в разделяемой памяти |

Два из них — падения, одно — тихая порча вывода, одно — падение только на зрении,
одно в поведении не видно вовсе. Тест «иголкой в стоге» третий дефект не ловил;
ловит его зависимость результата от числа слотов.

### Ускорено декодирование

Замеры на глубине 65000 токенов на слот, контекст 163840, `--parallel 2 --kv-unified`,
`kvarn5` для K и V плюс `--kv-tail-tokens 1024`. Метрика при двух слотах — окно, где
оба слота активны.

| | один слот | два слота, сумма | VRAM |
| --- | ---: | ---: | ---: |
| `preview-v0.4.4` как есть | 23.87 т/с | 7.10 т/с | 20066 МиБ |
| **этот форк** | **32.50 т/с** | **41.92 т/с** | 20066 МиБ |
| `q8_0` без хвоста, для сравнения | 32.79 т/с | 40.50 т/с | 22648 МиБ |

**×1.36 на одном слоте и ×5.9 на двух** относительно базы, при неизменной точности:
контрольная сумма генерации не менялась ни разу за всю работу.

При `--parallel 1` KVarN обгоняет `q8_0` и по скорости, и по памяти:

| `--parallel 1`, глубина 65000 | т/с | VRAM |
| --- | ---: | ---: |
| **`kvarn5` + хвост 1024** | **33.48** | 19996 МиБ |
| `q8_0` | 32.77 | 22498 МиБ |

Вклад отдельных правок:

| правка | один слот | два слота |
| --- | ---: | ---: |
| план чтения без красно-чёрного дерева | +9.8% | +13.7% |
| порядок плана чтения по ячейке | +0.5% | ×2.19 |
| порог `n_q` для split-декода | +0.3% | ×1.30 |
| пропуск полностью замаскированных сплитов | −0.5% | +27% |
| ядро дескрипторов: блок 128 → 1024 нитей | — | −13% времени шага |
| сплит 128 + починка выбора геометрии | +4.7% | 0% |
| перестановка строк матричного фрагмента | +2.5% | +5.0% |
| потолок регистров ради четырёх блоков | +1.5% | +15% |

### Спекуляция: компактный черновой кэш MTP

Черновой контекст MTP держал свой единственный слой `nextn` в честном f16 и платил за
него **832.00 МиБ** при контексте 212992 и четырёх слотах — вторая по величине статья
цены MTP после рекуррентного состояния цели. Теперь он умеет KVarN, и тот же слой
стоит **131 МиБ** при `kvarn2`.

Это единственный кэш, где потеря точности не может изменить ответ: голова MTP только
**предлагает** токены, а каждое предложение цель проверяет своим собственным кэшем.
Ослабление чернового кэша способно снизить приём, но не испортить вывод. На замерах
приём не упал — он вышел даже чуть **выше**, чем у f16 (0.778 против 0.769 при
`--spec-draft-n-max 2` и 0.875 против 0.871 при `n_max 1`, глубина 45283). Разница
мала, воспроизвелась в повторах, и объяснения ей у нас нет. Читать это как
«грубый черновик предсказывает лучше» не следует.

Включается так:

```bash
--spec-draft-type-k kvarn2 --spec-draft-type-v kvarn2
```

Принимаются `kvarn2`..`kvarn8`, половина запроса достраивается, а не отвергается,
умолчание не меняется: без этих флагов черновой кэш остаётся f16.

Черновой кэш на KVarN заодно вскрыл провал скорости, который оказался не ценой кэша,
а ложным заявлением возможности. При `--spec-draft-n-max 2` кэш объявлял границу
суффиксного отката в один токен, которой `can_seq_rm()` на деле не применяет, поэтому
сервер создавал контрольную точку на каждом цикле спекуляции и сериализовал весь
черновой кэш квадратичным алгоритмом. При контексте 212992, четырёх слотах, глубине
20115 и черновике `kvarn2`: **42.70 → 59.40 т/с**, загрузка карты **63% → 99%**.

Цена всего встроенного MTP на этой машине, контекст 212992, четыре слота:
**было 2522 МиБ, стало 1814 МиБ.**

### Зрение: веса проектора в закреплённой хост-памяти

Веса мультимодального проектора можно положить в закреплённую хост-память, оставив
вычисления на ускорителе. На этой машине, Qwen3.8-27B и её проектор зрения:
**освобождается 886 МиБ видеопамяти**, кодирование картинки **медленнее на 5-16%**,
скорость языковой модели не затронута, а сгенерированный текст байт в байт совпадает
с эталоном на памяти устройства.

Побайтовое совпадение проверено **только при `--parallel 1`**. Про большее число
слотов оно не говорит ничего, и цитировать его так не надо.

**По умолчанию выключено.** Включается явно:

```bash
--mmproj-host-weights            # либо LLAMA_ARG_MMPROJ_HOST_WEIGHTS=1
--no-mmproj-host-weights         # парный выключатель
```

Без флага форк ведёт себя ровно как раньше, и ни одна точка кода не смотрит на
окружение ради этого режима.

#### Почему у апстрима этот путь закрыт и что мы выяснили

Апстрим прибивает `devices[].integrated` к `false` с комментарием про порчу вывода.
Порча настоящая. Она не в железе и не в весах.

llama.cpp намеренно кладёт **входные** тензоры модели в тот же закреплённый хост-буфер
(«use the host buffer of the first device CPU for faster transfer of the intermediate
state»). Пока CUDA этот тип буфера «не поддерживает», планировщик обязан копировать
входы в видеопамять, а перед копией зовёт `ggml_backend_synchronize()`. **Эта копия —
единственный барьер** между записью входов процессором и чтением их ускорителем:
явную синхронизацию апстрим ставит только под `cparams.pipeline_parallel`. Стоит
объявить тип буфера поддержанным — копия исчезает, вместе с ней барьер, и
`set_input()` следующего ubatch пишет в память, которую ядра предыдущего ubatch ещё
читают.

Доказано тремя замерами: открытие общего типа буфера **без переноса единого веса
проектора** портит вывод, причём с побитово тем же хешем — значит веса ни при чём;
`CUDA_LAUNCH_BLOCKING=1` чинит вывод побайтово, не трогая ничего больше; дамп
планировщика `## SPLIT #1: CUDA0 # 8 inputs: [model.input_embed] ...
[attn_inp_kq_mask]` превращается в `# 0 inputs`.

Решение — отдельный тип буфера `CUDA_Host_W` только под веса. Получить его можно
единственным способом: спросив адрес у реестра бэкендов по имени, поэтому ни один
тензор языковой модели в него не попадёт, а барьер планировщика на входах остаётся на
месте. Веса пишутся один раз при загрузке, до первого счёта, — гонки для них не
существует по построению.

Мы полагаем, что этот разбор **объясняет** и открытый апстримный issue
[#25992](https://github.com/ggml-org/llama.cpp/issues/25992), где сервер при четырёх
слотах выдаёт чужой ответ дословно. Сами мы этот issue не воспроизводили и правку туда
не отправляли — совпадает механизм, и дальше этого утверждение не идёт.

### Покрытие тестами

Набор приведён в честное состояние — **97 из 97** зелёных, около 216 с. Разобраны три
падения, которые были в базе (устаревшее ожидание в `test-kvarn`, молчаливое падение
`test-arg-parser`, четыре теста моделей под `GGML_BACKEND_DL`), и закрыты две дыры в
покрытии: отдельный `tests/test-kv-group-claim.cpp` с отрицательным контролем на
резервирование группы и матрица естественного выбора ширины тайла запроса. Черновой
запрос KVarN добавил в `test-arg-parser` ещё четыре блока.

Прогнать:

```bash
cmake -B build -DLLAMA_BUILD_TESTS=ON <остальные опции>
cmake --build build -j"$(nproc)"
ctest --test-dir build --output-on-failure
```

## Что осталось незакрытым

* **Первый запрос после старта может отличаться при черновом кэше KVarN.** При
  `--parallel 1`, temperature 0, top-k 1, `--spec-draft-n-max 2`, глубине около 2123 и
  одном конкретном промпте первый запрос после старта сервера даёт другое (не
  испорченное — столь же устойчивое) продолжение, чем все последующие. Нужны
  одновременно `--parallel 1`, эта глубина и этот промпт; разогревочный запрос в
  девять токенов снимает аномалию до конца жизни процесса.
  `GGML_KVARN_SPLIT_MAX_Q=1` убирает её полностью, то есть живёт она в маршруте
  split-декода при `n_q > 1`. Замерами отброшены: контрольная точка черновика,
  неинициализированная память, ленивый выбор геометрии, правка `p_sh` и графы CUDA.
  **Причина не найдена.**
* **Почему более грубый черновой кэш попадает чуть лучше — не объяснено**, см. выше.
* Побайтовая проверка `--mmproj-host-weights` сделана только на одном слоте.

## Как собрать

### Docker (рекомендуется)

Образ собирается прямо из дерева репозитория, ничего доклонировать не надо.

```bash
docker build -f docker/Dockerfile.ci -t beellama-kvarn:local .
```

По умолчанию берётся набор архитектур CUDA
`75-virtual;80-virtual;86-real;89-real;90-virtual;120a-real;121a-real` — тот же, что
ggml выбирает сам для CUDA 13. Если карта одна, сборка сильно ускоряется указанием
только её:

```bash
docker build -f docker/Dockerfile.ci --build-arg CUDA_ARCHS=86 -t beellama-kvarn:local .
```

### Готовый образ из GHCR

```bash
docker pull ghcr.io/valujin/beellama-kvarn:latest
```

### Как это собирается в CI

Образ со всеми архитектурами CUDA собирается в GitHub Actions
([.github/workflows/docker-image.yml](.github/workflows/docker-image.yml)) и
публикуется в GHCR. Одной задачей это не укладывается: замер на бесплатном
раннере даёт **137 минут на одну архитектуру** при лимите задачи 6 часов, а в
наборе семь `--generate-code`. Места при этом хватает с запасом — у раннера
145 ГБ, сборка занимает 11.

Поэтому объектные файлы разложены по шести шардам. Все шарды конфигурируют
сборку одинаково через [.github/ci-configure.sh](.github/ci-configure.sh),
поэтому ccache-ключи у них совпадают с ключами финальной сборки: каждый шард
компилирует свою долю и сохраняет свой кусок кэша, а финальная задача сливает
куски и проходит сборку на попаданиях, оставаясь только с линковкой. Готовые
бинарники упаковываются [docker/Dockerfile.package](docker/Dockerfile.package).

Шардировать по архитектурам нельзя: ccache ключует по всей командной строке,
включая список `--generate-code`, поэтому одноархитектурная компиляция не даёт
ни одного попадания для многоархитектурной.

### Нативно

```bash
cmake -B build -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_CUDA=ON \
  -DGGML_CUDA_FA_ALL_QUANTS=ON \
  -DGGML_NATIVE=OFF \
  -DGGML_CPU_ALL_VARIANTS=ON \
  -DGGML_BACKEND_DL=ON \
  -DBUILD_SHARED_LIBS=ON \
  -DLLAMA_CURL=ON \
  -DLLAMA_BUILD_TESTS=OFF \
  -DLLAMA_BUILD_EXAMPLES=OFF \
  -DLLAMA_BUILD_TOOLS=ON
cmake --build build -j"$(nproc)" --target llama-server
```

**`GGML_NATIVE=OFF` намеренно.** `-march=native` делает CPU-ядра llama.cpp примерно на
40% медленнее: ядра написаны интринсиками, варианты собираются явными флагами фич с
обычным `-mtune` и выбираются в рантайме, а нативная сборка ломает этот механизм и
портит решения автовекторизатора. Поэтому здесь тот же подход, что у апстрима:
`GGML_CPU_ALL_VARIANTS` + `GGML_BACKEND_DL`.

## Как запустить

```bash
docker run --rm --gpus all -p 8080:8080 \
  -v /path/to/models:/models \
  ghcr.io/valujin/beellama-kvarn:latest \
  --model /models/your-model.gguf \
  --host 0.0.0.0 --port 8080 \
  --ctx-size 65536 \
  --n-gpu-layers 99 \
  --flash-attn on \
  --cache-type-k kvarn5 --cache-type-v kvarn5 \
  --kv-tail-tokens 1024
```

`--kv-tail-tokens 1024` стоит указывать явно: без него хвост точности не включается.
Компактный черновой кэш MTP добавляется флагами
`--spec-draft-type-k kvarn2 --spec-draft-type-v kvarn2`, веса проектора в хост-памяти —
флагом `--mmproj-host-weights`. Про сами типы кэша и их выбор — в
[README.upstream.md](README.upstream.md).
